Application Development

App development is where software engineering, systems architecture, and applied AI converge into something a user can actually touch. Most ML practitioners are trained on models and experiments but have little exposure to the plumbing that surrounds them — the APIs, databases, background workers, deployment pipelines, and real-time data flows that determine whether a product actually works at scale. This series closes that gap.

About This Series

This series covers the theory and practice of building data-driven applications: from the first HTTP endpoint through Docker-compose dev environments, async pipelines, vector search, and multimodal AI. It is organized around two threads that run in parallel: (1) general software engineering concepts applicable to any application, and (2) a concrete project — an AI-powered photo library — that progressively assembles those concepts into a working system.

Audience. Someone trained in machine learning or AI engineering, and so are comfortable with Python and NumPy, have worked with APIs or cloud services, and understand the ML stack. What you want is a grounded, practice-first treatment of the application layer: HTTP services, relational databases, event-driven data pipelines, containerization, and the integration patterns that hold them together.

Stack. The series uses tools chosen for clarity and real-world relevance: Flet for cross-platform desktop UI, FastAPI for the API layer, PostgreSQL + pgvector for structured and vector storage (via Docker), boto3 for S3 access, CLIP for local embeddings, and GPT-4o-mini for multimodal summaries. The goal is a minimal, composable stack where each layer is visible and teachable — not a framework that hides the complexity.

The main project is a personal photo library application — a ground-up reimplementation of the ideas behind Apple Photos — that ingests 1 TB of photos from S3, extracts EXIF metadata and CLIP embeddings, clusters faces into people albums, and supports natural-language queries and AI-generated narrative summaries of time periods. The project is deliberately ambitious: the challenges it poses (batch ETL at scale, approximate nearest-neighbor search, async progress streaming, multimodal retrieval) are exactly the challenges that distinguish senior engineers from junior ones.

NBX: Compute Platform

A five-notebook series that builds a production-grade ML compute platform — machine registry, task queue, live monitoring dashboard, and multi-provider dispatch — from scratch. The goal is a system where submitting a training job to a RunPod pod, an AWS instance, or a bare SSH host looks and feels identical, with progress, logs, and outputs streaming back to a local Flet UI in real time.

# Title Key Topics
NBX:01 Platform Architecture System design principles, provider abstraction layer, job spec schema, pydantic-settings config, secrets management, project scaffold
NBX:02 Registry & Dashboard Provider adapter pattern (RunPod / AWS / SSH), machine CRUD API, async health polling, Flet live resource dashboard with CPU / RAM / disk charts
NBX:03 Job Packaging & Execution tar.gz packaging, rsync-based sync, Runner abstraction (notebook / script / project), papermill param injection, SSH remote execution via asyncssh
NBX:04 Task Queue & Dispatch asyncio.PriorityQueue internals, job lifecycle FSM (pending → running → done / failed), provider selection strategy, parallel job concurrency control
NBX:05 Log Streaming & Artifacts WebSocket log fan-out, subprocess stdout / stderr capture, structured log events, artifact download via SCP, job history persistence, dev-mode file watching

See the NBX series index to get started.

Coding Agent From Scratch

A seven-notebook series that builds a complete async AI coding agent — similar in architecture to Claude Code — from first principles, and wraps it in a Flet desktop and web application. The agent code lives in src/notebooks/agent/ as an importable package; every notebook adds one layer of the stack.

# Title What We Build
CDA:01 Streaming LLM Client Async streaming wrapper for OpenAI-compatible APIs
CDA:02 The Tool System 7 builtin tools, ToolRegistry, Pydantic schemas
CDA:03 The Agent Loop Session + Agent: full multi-turn agentic loop
CDA:04 Hardening the Agent Context pruning, compaction, loop detection, approval policies, sub-agents
CDA:05 GUI 1: Chat Interface Flet chat application with streaming tool-call cards
CDA:06 GUI 2: Tools & Persistence Network/memory tools, session save/load, slash commands
CDA:07 GUI 3: MCP Integration Connect MCP servers via stdio & HTTP; /mcp command

See the CDA series index to get started.

Prerequisites

  • Python 3.13+, comfort with async/await, basic familiarity with HTTP
  • Cloud fundamentals: S3 object storage, environment variables, basic IAM / credentials
  • Part I (01, 03) is self-contained; Parts II–V assume you have read Part I or have equivalent Flet experience
  • Part III onward assumes you have a working Docker installation and an AWS account with an S3 bucket
  • No GPU is required: CLIP runs on CPU for the purposes of this series

How to Read This Series

If you are new to app development: Start at 01 and work forward sequentially. Each notebook prepares the ground for the next. The Flet notebooks (Part I) are lighter warm-up material; the real depth begins at 05.

If you already know Flet: Skip 01 and 03 and start at 05. Refer back to the Flet notebooks only when the integration notebooks (11–14) introduce new UI patterns.

If you only want the photo app: Read 05 → 06 → 07 → 08 → 09 → 10 → 11 → 12 → 13 → 14 in order. Each notebook adds one layer to the same codebase.

If you are here for the tooling: NBX is self-contained and can be read independently of the photo app project. For research infrastructure tooling, see the Tooling series.
